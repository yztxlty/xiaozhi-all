# 文档治理规范

> 状态：基线生效
> 版本：v0.1
> 更新日期：2026-08-28

## 目标

保证项目决策可追踪、实现可复现、测试可核验、发布可回滚，避免聊天记录或个人记忆成为唯一事实来源。

## 文档头

除目录索引和模板外，正式文档必须包含状态、版本、更新日期。涉及具体模块时增加责任模块；涉及决策时增加架构决策记录编号。

## 命名

- 生命周期目录使用两位数字前缀和中文名称，例如 `02-架构`。
- 正式文档使用清晰、完整的中文文件名，正文、标题、表头和说明文字均使用中文。
- 架构决策记录使用 `架构决策-0001-中文标题.md`。
- 测试报告使用 `年-月-日-测试范围-测试报告.md`。
- 发布记录使用 `版本号-年-月-日.md`。
- 第三方产品名、芯片型号、协议字段、接口路径、环境变量、命令和代码标识保留原文，并使用代码格式标识。

## 事实源优先级

发生冲突时按以下顺序处理：

1. 已生效的产品与需求基线。
2. 已接受且未被替代的架构决策记录。
3. 已冻结的协议与数据契约。
4. 自动化测试、真机验收和发布证据。
5. 当前实现代码。
6. 调研记录、会议记录和聊天记录。

代码与高优先级文档不一致时，不得默认为代码正确，必须通过变更流程修正文档、代码或两者。

## 评审与更新

- 需求文档：产品、架构、测试共同评审。
- 架构与协议：设备、服务端、客户端和测试共同评审。
- 安全相关：安全检查通过后方可基线化。
- 发布与运维：发布负责人和运维负责人共同确认。
- 每次正式发布检查一次失效链接、过期方案和未关闭风险。

## 禁止内容

- 真实密钥、令牌、Cookie、证书私钥和生产数据库连接信息。
- 未脱敏用户录音、转写、手机号、设备 ID 和账号信息。
- 没有环境、样本和统计口径的性能结论。
- 使用“应该、可能、差不多”替代可复现验收标准。
- 使用未编号的口头决定覆盖既有架构决策记录。

## 文档完成定义

一份文档只有同时满足以下条件才可标记为“基线生效”：目标与边界明确、输入输出明确、异常与回滚明确、验收方式明确、关联文档可访问、无敏感信息。
