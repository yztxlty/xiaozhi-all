# 设备统一云端语音接口与多端流式接入代码执行计划

> **执行要求：** 每个任务按“先写失败测试→确认红灯→最小实现→确认绿灯→受影响回归→提交”执行。当前主工作区已有用户未提交改动，执行者不得回退、覆盖或批量格式化无关文件。

**目标：** 让 ESP32 固件只修改 `CONFIG_OTA_URL` 即可接入 `xiaozhi-all` 完成全链路流式语音对话，同时保留当前 H5 链路，并为 T5 等设备提供低耦合接入边界。

**架构：** 新增独立的 `xiaozhi` 设备网关和 OTA 兼容接口；设备网关把小智 WebSocket v1 的控制消息与裸 `Opus` 音频转换成统一会话事件。H5 继续使用现有 PCM 网关；两者只共享会话运行时和 Provider 契约。Pipecat 承担实时管线，`xiaozhi-esp32-server` 的设备协议作为兼容基线，LiveKit Agents 的轮次检测、抢占式生成和打断语义通过独立组件复用。

## 当前执行状态（2026-08-29）

已落地设备 Profile、OTA 响应、WebSocket v1、`libopus` 编解码边界、设备输出适配器、独立设备服务入口和 Dify→Pipecat 增量文本适配；全量自动化测试为 `145 passed`。真实本地联调已验证 OTA 200、合法鉴权 WebSocket、`hello` 和 `ping`，非法鉴权返回 `1008`；85 环境已验证真实 `Opus → ASR → LLM → TTS → Opus` 流式闭环。针对实体设备停留“聆听中”的问题，已移除设备连接阶段阻塞式 Provider 预热，并增加实时 ASR 收尾、服务端静音边界与下一轮队列隔离；修复版已发布并通过两轮真实设备协议语音回归。

当前剩余验收不是代码占位：需要实际 ESP32 固件烧录后验证物理扬声器、连续三轮、播放中打断、断网重连和弱网稳定性；T5 目前完成 Profile/PCM 适配自动化测试，暂无真实 T5 硬件。

**技术栈：** Python 3.12、`websockets`、`httpx`、`pipecat-ai==1.8.1`、现有 ASR/LLM/TTS Provider、`libopus` 或已锁定的 Python Opus 封装、ESP-IDF 固件协议 v1。

## 全局约束

- 生产设备只修改 `CONFIG_OTA_URL`；服务端通过 OTA 响应下发 `websocket.url`、`websocket.token`、`websocket.version`。
- 设备协议首期固定 WebSocket v1、16 kHz、单声道、60 ms、裸 `Opus` Binary Frame。
- 服务端返回消息必须保持固件现有 `hello`、`stt`、`tts`、`llm`、`mcp`、`error` 语义。
- H5 现有 PCM 输入输出、消息格式和行为不得改变；设备网关不得修改 H5 `handler()`。
- 统一运行时不得导入设备专用网关模块；设备差异只存在于适配器、Profile、编解码器和消息映射层。
- 所有外部 Provider 调用必须支持超时和取消；所有实时队列必须有上限或明确的背压策略。
- 所有新增行为先写失败测试；不得以接口返回 200、服务启动或截图代替全链路验收。
- 不提交 `.env`、真实 Token、录音、构建物、`.DS_Store`、`__pycache__` 或临时日志。
