# 工程开发规范

> 状态：基线生效
> 版本：v0.2
> 更新日期：2026-08-30

## 开发流程

1. 需求和验收条件进入基线。
2. 架构变化新增 架构决策记录，协议变化先更新契约测试。
3. 新功能和缺陷修复执行 测试驱动开发：失败测试、最小实现、通过、回归。
4. 提交前运行格式、静态检查、单元测试、集成测试和敏感信息扫描。
5. 实时链路变更增加弱网、取消、迟到帧和资源释放测试。
6. 新增或合并协议入口时，必须先做真实首帧闭环测试：客户端建立连接、发送合法首帧、服务端返回协议握手响应；不得只检查路由注册、源码文本或进程健康。
7. 统一入口按首帧分流时，必须覆盖每一种协议分支的最小真实请求，并验证异常输入会返回明确协议错误而不是处理器崩溃。

## 代码原则

- 终端、会话编排、模型提供方和业务服务按接口解耦。
- 所有阻塞 SDK、文件和网络调用必须隔离出异步事件循环。
- 队列必须有上限、超时、背压和丢弃策略。
- 重试必须幂等；部分输出后重试必须创建新生成任务。
- 每个外部调用必须支持 deadline，并尽可能向下传播取消。
- 禁止通过临时文件和对象存储实现实时首音。
- 协议入口依赖的模块、异常类型和适配器必须在同一提交中由可执行测试覆盖；静态源码断言只能作为补充，不能替代运行时测试。

## 版本控制与依赖

- 分支使用 `feature/`、`fix/`、`docs/`、`release/` 前缀。
- 提交保持单一目的，不提交 `.env`、构建物、日志、录音和密钥。
- 依赖必须锁定版本并记录许可证；升级需要回归和安全扫描。
- 主分支只接收通过测试和评审的变更，不允许强推。

## 实时协议发布门禁

- 发布前必须执行一次设备协议真实握手，并断言返回 `hello`、会话标识和音频参数。
- 发布前必须至少完成一轮真实或等价的“音频输入 → ASR 结果 → LLM 回复 → TTS 音频输出”闭环；连续第二轮必须验证，防止流式编解码器或会话资源复用失败。
- 健康检查、HTTP `200`、静态页面可访问和模拟器通过均不能替代真机验收。
- 入口异常必须有服务端日志和客户端可见错误；禁止让异常穿透到 Web 框架导致连接无响应。
- 发布脚本切换候选版本后，必须再次验证当前活动容器的镜像版本和协议握手结果；验收中断不得把旧版本误报为新版本。

## 完成定义

代码、测试、文档、指标、错误处理、配置、迁移和回滚均有证据；真机相关能力必须通过真机验收，不能以模拟器或接口 200 替代。
