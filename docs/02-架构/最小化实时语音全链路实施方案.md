# 最小化实时语音全链路实施方案

> 状态：基线生效
> 版本：v0.1
> 更新日期：2026-08-28
> 适用阶段：ESP32 真机最小闭环
> 责任模块：实时协议网关、语音会话运行时、模型路由器、语音路由器

## 一、目标与结论

本方案用于在 `xiaozhi-all` 中建立一套面向智能硬件、网页端和移动端的实时语音对话最小闭环。ESP32 是首个接入和真机验收终端，不是架构中心；后续接入 T5、其他低成本芯片、网页端和移动端时，不得重写核心会话、模型和记忆逻辑。

首期采用以下组合：

- 使用小智 WebSocket 协议承载 ESP32 控制消息和双向 Opus 音频。
- 直接引入 Pipecat 作为服务端实时音频帧管线和会话编排基础。
- 使用真实已部署的 Dify Chatflow 作为首个大语言模型提供方。
- 使用腾讯实时语音识别作为付费质量和延迟基线。
- 使用现有火山引擎双向流式语音合成作为首个语音合成提供方。
- 使用 FunASR、sherpa-onnx 作为本地语音识别候选，通过同一契约进行影子评测。
- 将 CosyVoice 作为后续本地高质量语音合成候选，不作为最小闭环的启动依赖。

首期使用一个 Python 进程运行模块化单体，不为未经压测证明的扩容需求提前拆分微服务。代码模块保持独立契约和单向依赖，未来可以按模块拆进程，但设备协议和业务接口不得因此改变。

## 二、真实旧系统证据

### 2.1 Dify

旧系统通过 `chat-ai/common/config.ini` 的 `[dify]` 配置调用 Dify：

```text
基础地址：http://agent.gwcz.online/v1
聊天接口：POST /chat-messages
完整接口：http://agent.gwcz.online/v1/chat-messages
响应模式：streaming
```

这说明当前已经部署并被 `chat` 使用的是 Dify Chatflow/Advanced Chat Service API，而不是纯 Workflow App 的 `POST /workflows/run`。

旧系统还存在 `ip_url` 自定义消息管理接口，用于修改或批量删除 Dify 消息。该接口属于旧系统会话耦合能力，新项目不调用、不迁移，也不将其作为大语言模型 Provider 契约的一部分。

当前 Dify 基础地址使用明文 HTTP。Bearer 应用密钥、角色设定、短期上下文和长期记忆会随请求传输，因此生产上线前必须升级为可信 HTTPS；在此之前只允许用于受控开发联调，不得通过公网承载真实用户隐私数据。

### 2.2 ASR

旧系统中的移动端接口 `POST /voiceConvertText` 仍固定返回“测试语音转文字”，没有调用真实 ASR。腾讯代码使用 `CreateRecTask`、`8k_zh` 和文件任务轮询，服务端地址为：

```text
服务端点：asr.tencentcloudapi.com
区域：ap-guangzhou
旧引擎：8k_zh
```

该实现不满足实时语音对话的增量识别、端点检测和打断要求。新项目只复用腾讯云账号体系和区域配置，重新实现实时 ASR Provider，不复用旧文件识别业务代码。

### 2.3 TTS

旧系统真实主链路已经接入火山引擎 WebSocket 语音合成：

```text
服务地址：wss://openspeech.bytedance.com/api/v3/tts/bidirection
旧默认采样率：24000 Hz
旧默认格式：mp3
```

现有实现具备增量音频接收基础，但部分业务仍会汇总完整 MP3、转换 Base64、写临时文件或上传 TOS。新项目复用服务地址、账号和音色配置，改为文本流输入、PCM 音频块输出、服务端统一 Opus 编码，不再经过完整 MP3 和对象存储。

### 2.4 旧链路主要问题

- Dify 部分所谓流式路径先等待完整 HTTP 响应，再拆分 `response.text`，无法获得真实首字延迟。
- 旧 Dify 调用依赖 `conversation_id`，会话事实分散在 Dify 和业务系统。
- 移动端 ASR 是占位实现，腾讯 ASR 是 8k 文件任务，不是实时流式识别。
- TTS 存在完整文件、Base64 和对象存储中转，增加延迟、内存和带宽开销。
- 没有统一的 `session_id`、`turn_id`、`generation_id`、取消树和实际播放进度。
- ASR、LLM、TTS 分支混在聊天业务代码中，难以替换、测试和降级。

| 项目 | 首期使用方式 | 负责 | 明确不负责 |
| --- | --- | --- | --- |
| Pipecat | 锁定 `1.8.1` 版本直接依赖官方源码 | 实时处理管线、生命周期、背压、取消、打断和语音合成上下文 | 小智设备鉴权、业务记忆和产品语义 |

| FunASR | 独立本地 ASR Provider 候选 | 中文 Paraformer Streaming、VAD、标点 | 会话、LLM、设备协议 |
| sherpa-onnx | 低资源本地 ASR Provider 候选 | INT8 流式识别、端点检测和跨平台推理 | 业务路由和云端供应商管理 |

执行顺序固定为：直接使用官方依赖或稳定源码，其次使用薄适配层组合；只有上游缺陷或硬件约束已有复现证据时，才允许最小修补。禁止重写上述项目已经稳定提供的核心能力，也禁止复制无关业务层代码。第三方能力必须封装在基础设施层或具体模型适配器内，通过本项目稳定契约接入。

### 5.1 强制依赖规则

1. `voice-session-runtime/core` 只能依赖项目内部抽象契约和标准库。
2. `voice-session-runtime` 不得导入 Dify、腾讯、火山、FunASR、sherpa-onnx 或 CosyVoice SDK。
3. 网关不得访问数据库、记忆服务和具体 Provider。
4. Provider 之间不得互相导入或直接降级；降级只能由路由器执行。
5. `composition.py` 是唯一允许选择和装配具体 Provider 的位置。
6. Dify、腾讯、火山的鉴权字段不得进入统一领域对象。
7. 使用架构契约测试扫描导入关系，违反边界时持续集成直接失败。

## 六、Provider 设计

### 6.1 Dify Chatflow Provider

首期实现 `dify_chatflow`，不把真实 Chatflow 错写为 `dify_workflow`。

请求：

```http
POST http://agent.gwcz.online/v1/chat-messages
Authorization: Bearer ${DIFY_CHATFLOW_API_KEY}
Content-Type: application/json
```

```json
{
  "query": "用户本轮最终文本",
  "user": "内部匿名用户标识",
  "conversation_id": "",
  "response_mode": "streaming",
  "inputs": {
    "role_profile": "角色核心设定",
    "short_context": "最近有效对话",
    "long_term_memories": "长期记忆召回",
    "relationship_state": "关系与情绪状态",
    "scene": "companion_chat",
    "device_capabilities": "当前终端能力"
  },
  "auto_generate_name": false
}
```

规则：

- 每轮传空 `conversation_id`，忽略 Dify 返回的新会话标识。
- `xiaozhi-all` 是角色、上下文、记忆和实际听到文本的唯一事实源。
- 使用 `httpx.AsyncClient.stream()` 真正流式读取，不允许先调用普通 `post()` 等待完整响应。
- 识别 `message`、`agent_message`、`message_end`、`workflow_started`、`workflow_finished`、`error` 和 `ping`。
- 第一段文本到达后立即发布统一 `llm.text.delta`，不得等待 `message_end`。
- 用户打断时立即停止本地消费；取得 `task_id` 后尽力调用 `POST /chat-messages/{task_id}/stop`。
- 本地取消不依赖 Dify 停止成功；取消后的迟到文本不得进入 TTS、历史或记忆。
- 只有未来部署纯 Workflow App 后，才启用独立 `dify_workflow` Provider 和 `/workflows/run` 契约。

### 6.2 ASR Provider

统一输入：

```text
PCM S16LE
16000 Hz
单声道
每块 20～40 ms
```

统一事件：

```text
asr.speech_started
asr.partial
asr.final
asr.speech_ended
asr.failed
asr.cancelled
```

首期顺序：

1. 腾讯实时 ASR 作为付费质量与延迟基线。
2. FunASR Paraformer Streaming 作为中文本地部署候选。
3. sherpa-onnx INT8 Streaming Zipformer 作为低资源候选。

本地模型不得凭主观听感替换付费基线，必须使用同一中文陪伴语料，在相同机器和网络条件下对比字错率、首 partial、final 延迟、CPU、内存、并发和小时成本。

### 6.3 TTS Provider

统一输入事件：

```text
tts.start
tts.text.delta
tts.text.commit
tts.cancel
```

统一输出：

```text
PCM S16LE
24000 Hz
单声道
增量音频块
```

火山 Provider 使用真实地址：

```text
wss://openspeech.bytedance.com/api/v3/tts/bidirection
```

语音会话运行时将 PCM 统一编码为设备协商的 Opus 帧。不得直接把 Ogg Opus 容器、完整 MP3 或 Base64 字符串当作小智协议的原始 Opus 帧。

CosyVoice 仅以独立 Provider 方式部署。未通过首包延迟、显存、并发、自然度和稳定性门禁前，不进入默认主链路。

## 七、完整实时链路

```text
1. 设备建立 WebSocket 并发送 hello
2. 网关完成鉴权、协议版本和音频参数协商
3. 设备每 20 ms 上传一个 Opus 音频帧
4. 网关解码为 16 kHz PCM，并送入 Pipecat 输入管线
5. VAD 检测用户开始说话，立即触发旧轮次取消树
6. ASR 持续输出 partial；partial 仅用于界面，不提交 LLM
7. ASR final 产生后，会话服务组装角色、短期上下文和长期记忆
8. 模型路由器调用 Dify Chatflow 并逐行消费 SSE
9. 首个文本增量立即进入语义分句器
10. 达到自然语义边界后，文本增量送入火山双流式 TTS
11. TTS PCM 音频块经服务端 Opus 编码后下发设备
12. 设备播放并回传播放进度或播放完成事件
13. 只有实际播放过的 AI 文本才提交到历史和长期记忆候选
```

### 7.1 文本分句策略

- 首段优先低延迟，达到完整短句或约 12～24 个中文字符即可提交 TTS。
- 后续优先以 `。！？；` 等自然边界提交。
- 超过最大等待时间仍无标点时，按安全语义边界切分。
- 括号说明、Markdown、链接和工具中间结果不得直接朗读。
- 被取消轮次剩余文本不得继续合成。

## 八、打断与取消

每个用户轮次必须具有以下标识：

```text
session_id
turn_id
generation_id
tts_stream_id
playback_id
```

用户说话触发打断时，执行顺序固定为：

```text
1. 设备立即停止当前播放
2. 清空设备和服务端下行音频队列
3. 取消当前 TTS 流
4. 取消文本分句器和 Dify 本地事件消费
5. 尽力调用 Dify Stop API
6. 标记当前生成任务已取消
7. 丢弃所有旧 generation_id 的迟到事件
8. 开始新的 ASR 用户轮次
```

停止 Dify、腾讯或火山远端任务失败，不得阻塞本地停止播放。误打断恢复只能恢复尚未丢弃且设备未确认清空的音频，不得重新朗读用户已经听过的内容。

## 十、最小实施阶段

### 阶段 0：配置与安全门禁

- 为 Dify 增加 HTTPS 入口并验证证书。
- 建立 `.env.example`，只保存变量名和非敏感默认值。
- 将旧 `config.ini` 的密钥迁移到服务端环境变量或密钥系统。
- 对仓库、日志和测试夹具执行密钥扫描。

退出条件：真实密钥不进入 Git、日志和客户端；Dify 使用 HTTPS。

### 阶段 1：模块骨架与契约

- 建立实时服务组合根、网关、语音会话、模型路由器和语音路由器。
- 定义统一会话、ASR、LLM、TTS 和取消事件。
- 建立禁止跨层导入的架构契约测试。
- 引入并锁定 Pipecat 版本，只启用最小依赖集合。

退出条件：所有核心模块可以使用内存 Fake Provider 跑通，架构边界测试通过。

### 阶段 2：真实 Dify Chatflow

- 实现 `dify_chatflow` 的配置、映射、SSE 解析、取消、错误和指标。
- 使用真实地址验证 `message`、`message_end` 和内部工作流事件。
- 验证每轮传空 `conversation_id`，显式上下文在服务重启后仍可独立运行。

退出条件：真实 Dify 真流式响应、首增量、取消和错误路径全部通过。

### 阶段 3：真实 ASR 与 TTS

- 实现腾讯实时 ASR Provider。
- 实现火山双向流式 TTS Provider。
- 建立 PCM、Opus、采样率和帧时长统一处理。
- 删除最小链路中的 MP3、Base64、临时文件和 TOS 中转。

退出条件：预录音频可以完成 ASR → Dify → TTS 流式闭环。

### 阶段 4：ESP32 真机闭环

- 实现小智 WebSocket 握手、Opus 上下行和控制消息。
- 实现用户打断、迟到帧隔离、播放进度和断线清理。
- 在真实开发板完成连续对话、弱网和 30 分钟长稳测试。

退出条件：所有真机性能门禁达到要求，无旧音频串流和会话污染。

### 阶段 5：本地模型成本优化

- 接入 FunASR 和 sherpa-onnx 影子流量。
- 评测 CosyVoice 的首包、显存、并发、自然度和小时成本。
- 只有达到质量与稳定性门槛后，才允许通过配置切换主 Provider。

退出条件：形成可复现评测报告和明确主备路由策略。

## 十一、测试与性能门禁

| 指标 | 首期门禁 |
| --- | --- |
| 100 轮真机有效对话成功率 | 不低于 99% |
| 用户停说到 ASR final P95 | 不高于 350 ms |
| Dify 首个文本增量 P95 | 不高于 450 ms |
| TTS 首个音频块 P95 | 不高于 300 ms |
| 用户停说到设备首音 P95 | 不高于 1.2 s |
| 用户打断到设备停止播放 P95 | 不高于 250 ms |
| 连续运行 | 30 分钟无崩溃、无明显内存增长 |
| 取消后的旧文本和旧音频 | 0 条进入新轮次 |
| 密钥泄露 | 0 |

必须覆盖：

- Dify 所有已知 SSE 事件、半包、粘包、空行、未知事件和中途断流。
- ASR partial/final 顺序、无语音、噪声、超时和取消。
- TTS 首包、文本增量、尾包、取消、断连和重连。
- ESP32 重连、重复 hello、弱网、丢包、迟到帧和播放队列清空。
- 首增量前 Provider 降级和首增量后禁止拼接第二份回复。
- 用户实际听到文本的提交边界。

## 十二、风险与控制

| 风险 | 控制措施 |
| --- | --- |
| Dify 当前为 HTTP | HTTPS 是生产发布阻断门禁 |
| Pipecat 升级造成接口漂移 | 锁定精确版本，升级必须跑契约、延迟和真机回归 |
| ESP32 重连产生幽灵连接 | 以收到合法 `hello` 作为连接认领条件，旧连接异步关闭 |
| 本地 ASR 准确率不足 | 先影子评测，不直接替换付费基线 |
| CosyVoice 资源占用过高 | 独立进程和可选部署，不进入最小启动依赖 |
| Dify 工作流节点过多导致 TTFT 上升 | 陪聊场景使用最短路径，以 TTFT 门禁阻断发布 |
| 用户打断后仍播放旧音频 | 使用 generation_id、playback_id 和队列清空确认隔离 |
| 多端接入导致业务逻辑复制 | 所有终端只实现网关适配，共享语音会话和 Provider 契约 |

## 十三、首期非目标

- 不部署或扩缩容 Dify。
- 不开发 Dify 管理后台和工作流编辑器。
- 不引入 Redis、Kafka、Kubernetes 和服务网格。
- 不同时引入 Pipecat 与 LiveKit 作为核心会话运行时。
- 不在首期部署 CosyVoice。
- 不开发计费、会员、完整用户中心和运营后台。
- 不修改 ESP32 已通过真机验收的界面、动画和分区资源。
- 不让 Dify、ASR 或 TTS Provider 直接访问业务数据库。

## 十四、验收结论标准

只有同时满足以下条件，才能宣布最小实时语音闭环完成：

1. ESP32 真机完成聆听、识别、思考、说话和再次开口打断。
2. Dify 使用真实 Chatflow 接口和真 SSE 流，不依赖 Dify 会话记忆。
3. 腾讯实时 ASR 和火山双向流式 TTS 的成功、失败和取消路径均有证据。
4. 全链路首音、打断、稳定性和成功率达到本方案门禁。
5. 旧生成任务的文本和音频不会进入新轮次、历史或记忆。
6. 代码依赖满足高内聚、低耦合边界，架构契约测试通过。
7. 仓库、日志、镜像和客户端不包含真实密钥。
8. Dify 生产调用已切换 HTTPS 并通过证书验证。
