# 推荐技术架构与代码组织详细设计

> 状态：评审中  
> 版本：v0.1  
> 更新日期：2026-08-28  
> 责任模块：实时服务、设备协议网关、语音会话运行时、模型路由器、语音路由器  
> 关联架构决策：架构决策-0001、架构决策-0003

## 一、文档目的

本文把“小智协议网关 + Pipecat + Provider 适配器”的推荐方案展开为可直接实施的架构和代码组织规范，解决以下问题：

- 当前优先接入 ESP32，但核心会话能力不能绑定 ESP32。
- 后续 T5、其他低成本智能硬件、网页端和移动端必须复用同一套语音会话内核。
- Dify、腾讯实时语音识别、火山引擎双向语音合成必须可替换，不得侵入领域层。
- 流式响应、用户打断、取消传播、实际播放提交和故障降级必须形成一个闭环。
- 项目首期保持模块化单体，避免过早拆分微服务，同时保留未来独立部署边界。

本文是代码组织和依赖方向的详细设计；产品范围以《需求基线》为准，协议字段以 `docs/03-协议` 下的已生效契约为准。

## 二、架构结论

### 2.1 推荐组合

| 层级 | 首期选择 | 作用 |
| --- | --- | --- |
| 设备接入 | 小智 WebSocket 协议 | 兼容当前 ESP32 的控制帧和双向 Opus 音频帧 |
| 会话内核 | Pipecat | 承载实时 Frame 管线、处理器生命周期、背压、打断和指标钩子 |
| 模型调用 | 阿里云通义千问 Qwen 3.7 Flash；Dify 保留可切换 | 当前低延迟主链路使用通义千问，Dify 恢复后继续作为可替换工作流能力 |
| 在线语音识别 | 阿里云 DashScope Paraformer Realtime v2 | 中文实时识别、临时结果和最终结果 |
| 在线语音合成 | 火山引擎 BigTTS v3 双向流 | 文字持续输入、音频块持续输出，避免完整 MP3 中转 |
| 本地候选 | FunASR、sherpa-onnx、CosyVoice | 通过相同契约做影子评测和后续成本优化 |
| Web/App 接入 | 后续 RTC 网关 | 首期不阻塞 ESP32；需要时可引入 LiveKit，不替换会话内核 |

### 2.2 不采用的方式

- 不复制 `xiaozhi-esp32-server` 全部业务层；直接复用其稳定协议、火山引擎双向流状态机和兼容测试经验。
- 不让 Pipecat 负责设备鉴权、角色记忆和 Dify 输入语义。
- 不让 Dify 保存项目会话事实；每轮由本项目传入角色、短期上下文和长期记忆。
- 不让网关直接调用 ASR、LLM 或 TTS Provider。
- 不在首期把每个目录部署成独立微服务。
- 不为尚未接入的 Provider 编写伪实现并宣称链路已完成。

## 三、总体逻辑架构

```text
ESP32 / T5 / 其他硬件            Web / App
          │                         │
          │ 小智 WebSocket          │ WebRTC（后续）
          ▼                         ▼
┌──────────────────┐       ┌──────────────────┐
│ 小智协议网关     │       │ RTC 协议网关     │
│ 鉴权/控制/Opus   │       │ 鉴权/媒体适配    │
└────────┬─────────┘       └────────┬─────────┘
         └──────────────┬────────────┘
                        ▼
┌──────────────────────────────────────────────┐
│ 语音会话运行时                               │
│ 会话状态机 / 轮次 / Pipecat / 背压 / 取消树 │
│ VAD / 打断 / 实际播放进度 / 迟到事件隔离    │
└───────────────┬───────────────────┬──────────┘
                │                   │
                ▼                   ▼
┌────────────────────────┐  ┌────────────────────────┐
│ 语音路由器             │  │ 模型路由器             │
│ ASR/TTS 统一契约       │  │ LLM 统一契约           │
│ 健康/超时/能力/降级    │  │ 健康/超时/能力/降级    │
└──────┬──────────┬──────┘  └───────────┬────────────┘
       │          │                     │
       ▼          ▼                     ▼
腾讯实时 ASR  火山双流式 TTS        Dify Chatflow
       │          │                     │
       └──── 本地候选 Provider ─────────┘
```

核心原则是“网关只翻译协议、运行时只编排会话、路由器只选择能力、Provider 只适配供应商”。任何跨越两层以上的直接调用都视为架构违规。

## 四、部署形态

### 4.1 首期：模块化单体

首期由 `apps/realtime-server` 作为唯一进程入口，在一个 Python 进程中装配：

- 小智 WebSocket 网关；
- 语音会话运行时；
- Pipecat 管线适配；
- 模型路由器及 Dify Chatflow Provider；
- 语音路由器及腾讯 ASR、火山 TTS Provider；
- 指标、日志、链路追踪和健康检查。

模块仍使用独立包、独立契约测试和明确依赖边界。只有压测证明网关、ASR/TTS 或模型调用存在独立扩缩容需求时，才拆为不同进程。

### 4.2 后续拆分条件

满足以下任一条件且有压测证据时，才允许拆分：

- 单一模块的资源曲线与其他模块明显不同；
- 故障隔离收益高于跨进程序列化和网络开销；
- 单进程无法满足目标并发或发布频率；
- Provider 需要独立网络、安全域或 GPU 资源池。

拆分后必须保持统一领域事件和 Provider 契约不变，终端协议不得感知内部部署变化。

## 六、模块职责和文件逻辑

### 6.1 `apps/realtime-server`

`realtime-server` 是组合根，不承载业务规则。

| 文件 | 责任 | 禁止事项 |
| --- | --- | --- |
| `settings.py` | 从环境变量构建各模块配置对象 | 不写真实密钥默认值，不把配置对象传入领域层 |
| `composition.py` | 创建 HTTP 客户端、Provider、路由器、会话运行时和网关 | 业务逻辑不得散落在装配代码中 |
| `bootstrap.py` | 管理启动、信号、优雅停止和资源关闭 | 不直接解析设备消息 |
| `health.py` | 聚合网关、路由器和 Provider 健康结果 | 健康检查不得发送真实对话请求 |

`composition.py` 是唯一允许同时导入具体 Provider 和抽象端口的文件。

### 6.2 `gateways/xiaozhi-websocket`

网关把小智协议转换为稳定领域输入，把领域输出转换回设备协议。

- `handshake.py` 校验 `hello`、协议版本、音频参数和设备能力。
- `authentication.py` 只调用设备鉴权端口，不直接访问业务数据库。
- `control_messages.py` 解析 `listen`、`abort`、`tts` 等控制消息。
- `audio_frames.py` 校验二进制帧大小、时序和 Opus 参数，不做 ASR。
- `transport.py` 负责收发、心跳、背压和断连，不保存会话业务状态。
- `connection_registry.py` 保存短生命周期连接映射，不作为会话事实源。

### 6.3 `services/voice-session-runtime`

会话运行时是全端共享的核心。ESP32、Web 和 App 只能通过端口向它输入音频和控制事件。

#### `core`

- `session.py` 定义 `CONNECTING → READY → LISTENING → THINKING → SPEAKING → CLOSED` 等合法状态迁移。
- `turn.py` 为每轮生成独立 `turn_id` 和 `generation_id`；旧代际事件不得污染新轮次。
- `events.py` 定义音频、转写、文本、播放、取消和错误领域事件。
- `cancellation.py` 建立 `session → turn → generation → provider request` 取消树。
- `ports.py` 只定义抽象协议，不导入 Pipecat、Dify、腾讯或火山 SDK。

#### `application`

- `run_session.py` 串联 ASR、LLM、TTS 和终端输出。
- `handle_interruption.py` 在用户说话时先停止本地下游消费，再尽力停止远端任务。
- `commit_turn.py` 只提交用户实际听到的 AI 文本，不提交已生成但未播放的尾部文本。

#### `infrastructure/pipecat`

- `pipeline_factory.py` 以会话为单位创建和关闭 Pipecat Pipeline。
- `frame_mapper.py` 是 Pipecat Frame 与项目领域事件之间的唯一转换点。
- `observers.py` 从 Frame 流记录首转写、首文本、首音频、打断完成和错误指标。

Pipecat 只存在于基础设施层；卸载或替换 Pipecat 时，`core` 和 Provider 契约不变。

### 6.4 `services/model-router`

模型路由器不保存会话，不理解设备协议，只接收完整的 `LLMRequest` 并输出统一事件流。

```text
LLMRequest
   │
   ▼
LLMRouter ──能力/健康/策略──► DifyChatflowProvider
                                  │
                 input_mapper ────┤
                 client/SSE  ─────┤
                 output_mapper ───┤
                 cancellation ────┤
                 metrics ─────────┘
                                  │
                                  ▼
       LLMStarted / LLMTextDelta / LLMCompleted
```

`dify_chatflow` 必须遵守：

- 每轮调用 `POST /v1/chat-messages`；
- `conversation_id` 固定为空；
- 使用 `AsyncClient.stream()` 和 `aiter_lines()`；
- 顶层 `answer` 到达后立即输出 `LLMTextDelta`；
- 首文本前最多重试一次，首文本后禁止自动重试拼接；
- 本地取消优先，远端 `/chat-messages/{task_id}/stop` 仅为尽力清理；
- 输入映射、SSE、HTTP、取消、指标各自单一职责；
- 日志、指标和异常不包含密钥、用户正文、角色全文和长期记忆。

### 6.5 `services/speech-router`

语音路由器通过统一契约隔离云服务和本地模型。

ASR 输入统一为会话内连续 PCM 音频块，输出至少包括：

- `asr.started`；
- `asr.partial`；
- `asr.final`；
- `asr.failed`；
- `asr.cancelled`。

TTS 输入为有序文本增量，输出至少包括：

- `tts.started`；
- `tts.audio.chunk`；
- `tts.completed`；
- `tts.failed`；
- `tts.cancelled`。

腾讯和火山供应商字段只能出现在对应 Provider 内。路由器基于能力、健康、语言、音色和实时性选择 Provider，不在 Provider 之间直接互相降级。

### 6.6 `packages`

`packages` 只保存跨模块稳定能力：

- `realtime-protocol`：协议版本、控制消息和统一事件标识；
- `audio-codec`：采样率、声道、帧时长、PCM/Opus 契约和测试向量；
- `provider-contracts`：跨模型和语音路由器复用的能力、健康和错误语义；
- `observability`：链路字段、指标名称、脱敏和结构化日志工具。

`packages` 不得导入 `apps`、`gateways`、`services` 或供应商 SDK。

## 七、强制依赖方向

```text
apps/realtime-server/composition
        │
        ├── gateways/xiaozhi-websocket
        ├── services/voice-session-runtime/application
        ├── services/voice-session-runtime/infrastructure/pipecat
        ├── services/model-router/providers
        └── services/speech-router/providers

gateways ───────────────► voice-session-runtime/core/ports
voice-session/application► voice-session-runtime/core
voice-session/core ──────► packages 中的稳定契约
model-router/providers ──► model-router/core
speech-router/providers ─► speech-router/core
```

强制规则：

1. `voice-session-runtime/core` 只能依赖标准库和稳定契约。
2. `core` 不得导入 `infrastructure`、具体 Provider 或应用入口。
3. 网关不得导入 Dify、腾讯、火山或 Pipecat。
4. Dify Provider 不得导入语音 Provider，Provider 之间不得互相调用。
5. 具体 Provider 的选择只出现在 `composition.py` 和路由配置中。
6. 供应商密钥类型不得进入统一领域对象。
7. 根级架构测试必须扫描 Python 导入并在违规时失败。

## 八、完整实时链路

### 8.1 建立连接

```text
设备连接 WebSocket
  → 解析 hello
  → 验证协议版本和音频参数
  → 调用设备鉴权端口
  → 创建 session_id
  → 创建会话级 Pipecat Pipeline
  → 返回 ready
```

握手失败时不得创建 Provider 请求；断连时必须取消当前会话树并释放管线。

### 8.2 正常语音对话

```text
设备 Opus 帧
  → 网关校验并解码/转交音频端口
  → VAD 与 ASR 流式处理
  → ASR partial 仅用于界面和端点判断
  → ASR final 创建 turn_id/generation_id
  → 会话服务装配角色、短期上下文、长期记忆
  → 模型路由器调用 Dify Chatflow
  → 首个 LLMTextDelta 立即送入 TTS
  → TTS 音频块经 Opus 编码发送设备
  → 根据设备播放确认更新实际听到进度
  → 仅提交实际听到文本和最终用户文本
```

禁止等待 LLM 完整回复后再启动 TTS，也禁止等待完整 TTS 文件后再发送设备。

### 8.3 用户打断

```text
用户说话/VAD 命中
  → 标记当前 generation 已取消
  → 停止向设备发送旧音频
  → 清空旧 generation 待发送队列
  → 取消本地 TTS、LLM、ASR 下游任务
  → 尽力调用供应商 stop/cancel
  → 丢弃携带旧 generation_id 的迟到事件
  → 根据实际播放进度提交已听到文本
  → 创建新 turn
```

打断正确性由 `generation_id` 隔离保证，不能依赖供应商及时停止。

### 8.4 断线与恢复

- 连接断开立即取消连接级发送任务，但会话是否保留由恢复策略决定。
- 恢复窗口内重新连接必须重新鉴权，并携带受签名保护的恢复标识。
- 未收到设备播放确认的音频不得推断为已经播放。
- 超过恢复窗口后关闭 session，不自动重放旧回复。

## 九、Pipecat 接入边界

Pipecat 作为成熟实时音频管线依赖直接引入，但只封装在 `infrastructure/pipecat`：

| 项目语义 | Pipecat 侧语义 | 适配位置 |
| --- | --- | --- |
| 终端输入音频块 | 输入音频 Frame | `frame_mapper.py` |
| ASR partial/final | 转写 Frame | `frame_mapper.py` |
| LLM 文本增量 | 文本 Frame | `frame_mapper.py` |
| TTS 音频块 | 输出音频 Frame | `frame_mapper.py` |
| 打断/取消 | 中断控制 Frame 和 Task 取消 | `pipeline_factory.py` |
| 首包和处理耗时 | Frame 观察器 | `observers.py` |

不得让业务代码继承 Pipecat 类作为领域模型；适配器负责转换，避免第三方版本升级扩散到全仓库。

Pipecat 版本必须精确锁定并经过以下验证后升级：

- ESP32 持续双向音频回归；
- 首字和首音频延迟回归；
- 真打断和误打断回归；
- 连接取消后无后台任务泄漏；
- Web/App 传输适配不改变会话领域事件。

## 十、状态与数据所有权

| 数据 | 唯一事实源 | 生命周期 |
| --- | --- | --- |
| WebSocket 连接 | 网关连接注册表 | 单次连接 |
| 会话状态 | 语音会话运行时 | 单次会话 |
| 当前轮次和代际 | 语音会话运行时 | 单轮对话 |
| 角色和关系状态 | 会话服务 | 跨会话 |
| 短期上下文 | 会话服务 | 配置窗口 |
| 长期记忆 | 记忆服务 | 跨会话 |
| Dify `conversation_id` | 不使用 | 每轮为空 |
| Provider `task_id` | Provider 适配器 | 单次供应商请求 |
| 实际听到文本 | 会话服务 | 跨会话记录 |
| 原始音频 | 默认不持久化 | 会话内短暂存在 |

Dify 不独立保存本项目的会话记忆。供应商返回的会话标识和任务标识只能用于当前请求控制，不得成为业务主键。

## 十一、配置和安全

- `settings.py` 只声明配置结构和环境变量名。
- Dify Key、腾讯 Secret、火山 Token 使用密钥管理或进程环境注入。
- 配置示例只写占位符，不复制 `chat-ai/common/config.ini` 的密钥。
- 当前 Dify HTTP 地址只允许受控开发联调；生产必须升级 HTTPS。
- 日志默认记录 `session_id`、`turn_id`、`generation_id`、Provider、耗时和错误码，不记录用户正文和完整角色记忆。
- 所有外部请求设置连接、读取、总时限和取消策略。

## 十二、错误、重试和降级

### 12.1 LLM

- 连接失败、429、502、503、504 在首文本增量前最多重试一次。
- 首文本增量后发生断流，不自动重试或切换 Provider，防止重复和语义拼接。
- 取消后的所有迟到增量按 `generation_id` 丢弃。

### 12.2 ASR

- 实时流中断后不得把不完整 partial 当作 final。
- 是否切换 Provider 由语音路由器决定，不能在供应商适配器内部切换。
- 切换时必须新建识别代际，防止两路结果混合。

### 12.3 TTS

- 已向设备发送音频后切换 Provider 可能导致音色突变，默认不做轮中降级。
- 首音频前失败可按路由策略重试或切换；首音频后失败返回统一终态并保留已播放进度。

## 十三、测试结构和门禁

| 测试层 | 核心内容 | 进入发布的证据 |
| --- | --- | --- |
| 包内单元测试 | 状态迁移、映射、SSE、错误分类 | 每个行为先失败再通过 |
| 根级契约测试 | 导入边界、事件字段、协议版本 | 架构违规直接失败 |
| 集成测试 | 网关→会话→模拟 Provider→音频输出 | 单进程完整闭环 |
| 延迟测试 | ASR partial/final、LLM 首增量、TTS 首音频 | 固定样本和统计口径 |
| 打断测试 | 本地立即停止、远端尽力取消、迟到事件丢弃 | 无旧音频和旧文本泄漏 |
| 真实服务测试 | Dify、腾讯、火山受控冒烟 | 不输出密钥和隐私数据 |
| 真机测试 | ESP32 连接、连续对话、打断、重连 | 真机记录和版本信息完整 |

根级最少需要以下架构断言：

- `voice_session.core` 不包含 Pipecat 和供应商导入；
- `xiaozhi_gateway` 不包含模型和语音 Provider 导入；
- Provider 目录之间没有交叉导入；
- 只有 `composition.py` 装配具体 Provider；
- 仓库不存在真实密钥和旧 Dify `ip_url` 调用。

## 十四、性能验收目标

以下是首期真机优化目标，不是当前已测结论：

| 指标 | 初始目标 | 统计方式 |
| --- | --- | --- |
| ASR 首个有效 partial | `P95 ≤ 350 ms` | 从有效语音帧进入服务端起 |
| 用户停说到 ASR final | `P95 ≤ 500 ms` | 固定中文语料 |
| LLM 首文本增量 | `P95 ≤ 1,200 ms` | 从发出 Dify 请求起 |
| 首文本到 TTS 首音频 | `P95 ≤ 500 ms` | 从首个可合成文本增量起 |
| 用户停说到设备首音频 | `P95 ≤ 2,000 ms` | ESP32 真机端到端 |
| 打断到停止旧音频发送 | `P95 ≤ 200 ms` | 从服务端确认用户说话起 |

每项必须同时记录网络、服务版本、设备固件、音频样本、样本数和 `P50/P95/P99`；未测量前不得写成“已达到”。

## 十五、实施顺序

### 阶段一：框架和契约

1. 建立根 Python 工作区和统一测试入口。
2. 建立 `packages` 稳定契约。
3. 建立网关、会话运行时、模型路由器和语音路由器包边界。
4. 增加根级架构依赖测试。
5. 建立 `realtime-server` 组合根和健康检查。

### 阶段二：Dify 最小文本闭环

1. 完成 Dify Chatflow 真流式 Provider。
2. 从旧项目配置中安全读取本地联调参数，不复制密钥。
3. 验证统一 LLM 事件顺序、取消和首增量延迟。

### 阶段三：实时语音闭环

1. 引入并锁定 Pipecat。
2. 接入腾讯实时 ASR。
3. 接入火山双向流式 TTS。
4. 完成 PCM/Opus Frame 映射和背压。
5. 用模拟传输完成进程内闭环。

### 阶段四：ESP32 真机

1. 完成小智协议握手和控制消息。
2. 完成双向 Opus 音频帧。
3. 验证连续多轮、打断、弱网和重连。
4. 记录端到端延迟并迭代优化。

### 阶段五：多端和本地模型

1. 增加 Web/App RTC 网关，不改会话内核。
2. 对 FunASR、sherpa-onnx、CosyVoice 进行影子评测。
3. 只有评测达到质量、延迟和成本门禁后才加入正式路由。

## 十七、架构完成定义

只有同时满足以下条件，才允许宣称“推荐架构骨架已完成”：

1. 目标包结构和根工作区可以一次安装、测试和启动。
2. 会话核心不导入 Pipecat 和任何供应商 SDK。
3. `composition.py` 能装配网关、会话运行时、模型路由器和语音路由器。
4. Dify 通过统一 `LLMProvider` 输出真流式事件。
5. 模拟 ASR/LLM/TTS 能跑通进程内完整事件链路。
6. 打断后旧 `generation_id` 的事件不会进入 TTS 或终端输出。
7. 架构测试、单元测试、集成测试和 `git diff --check` 全部通过。
8. 仓库不包含真实密钥、临时文件、缓存和无调用方的占位实现。
