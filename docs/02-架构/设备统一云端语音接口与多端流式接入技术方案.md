# 设备统一云端语音接口与多端流式接入技术方案

> 状态：方案已确认，待执行
> 适用项目：`xiaozhi-all`、`xiaozhi-175c-dev`
> 文档类型：架构与实施方案
> 更新日期：2026-08-29

## 1. 目标

设备端只修改一个统一云端 API 地址，即可切换到由 `xiaozhi-all` 提供的云端语音对话服务。设备端继续使用现有小智协议、消息名称、输入输出字段和 `Opus` 音频格式，不感知具体的 ASR（语音识别）、LLM（大语言模型）和 TTS（语音合成）厂商。

服务端需要同时满足：

- 完全兼容当前 ESP32 固件的 OTA、WebSocket 和语音消息契约；
- 支持 ESP32、未来 T5 等不同芯片和音频能力的设备接入；
- 支持 ESP32、H5、移动端及未来 WebRTC 端的全链路流式语音对话；
- 复用 `xiaozhi-esp32-server`、Pipecat、LiveKit Agents 的成熟能力；
- 通过组件适配器隔离设备差异和 Provider 差异；
- 新增设备协议不得修改或破坏当前 H5 流式语音链路。

## 2. 总体架构

```text
ESP32 / T5 等设备
        │ 小智 WebSocket、设备专用协议
        ▼
设备协议网关
        │ 设备事件、统一音频帧
        ▼
统一实时会话运行时
        ├── ASR Provider
        ├── LLM Provider
        ├── TTS Provider
        ├── 打断与取消
        ├── 轮次与状态机
        └── 播放确认与历史提交
        ▲
        │
H5 WebSocket / 移动端 / WebRTC 网关
```

核心运行时只处理统一内部事件，不直接处理 ESP32、T5 或 H5 的协议字段。不同端通过适配器完成以下转换：

```text
端侧输入协议 → 端侧适配器 → 统一内部事件
统一内部事件 → 端侧适配器 → 端侧输出协议
```

## 3. 设备端只需修改的配置

### 3.1 推荐方式：只修改 OTA 地址

固件当前配置项：

```text
CONFIG_OTA_URL
```

当前默认值：

```text
https://api.tenclass.net/xiaozhi/ota/
```

目标配置：

```text
https://api.example.com/xiaozhi/ota/
```

设备请求统一 OTA 接口后，由服务端返回 WebSocket 地址、Token 和协议版本。设备端不需要分别修改 WebSocket 地址、ASR 地址或 TTS 地址。

当前最小部署实现使用两个内部监听端口：`18766` 提供固件要求的 `POST /xiaozhi/ota/`，`18765` 提供 `/xiaozhi/v1/ws`。生产环境可由反向代理统一暴露为同一域名；设备仍只配置一个 `CONFIG_OTA_URL`，服务端返回的 WebSocket 地址由 `XIAOZHI_DEVICE_WS_URL` 配置。

### 3.2 当前固件已有的 WebSocket 配置

当前固件还支持以下编译配置：

```text
CONFIG_XIAOZHI_CUSTOM_WEBSOCKET_URL
CONFIG_XIAOZHI_CUSTOM_WEBSOCKET_TOKEN
CONFIG_XIAOZHI_CUSTOM_PROTOCOL_VERSION
```

对应的运行时 NVS 字段为：

```text
websocket.url
websocket.token
websocket.version
```

目标方案中，以上字段由统一 OTA 接口自动下发。它们保留用于本地开发和故障排查，但不作为生产环境的主要切换方式。

### 3.3 WebSocket 请求头

服务端必须兼容固件现有请求头：

```http
Authorization: Bearer <token>
Protocol-Version: 1
Device-Id: <设备 MAC 地址>
Client-Id: <设备 UUID>
```

## 4. OTA/激活接口契约

服务端提供：

```text
POST /xiaozhi/ota/
```

请求头保持固件当前实现：

```http
Activation-Version: 1 或 2
Device-Id: <设备 MAC 地址>
Client-Id: <设备 UUID>
User-Agent: <固件 User-Agent>
Accept-Language: zh-CN
Content-Type: application/json
```

请求体继续兼容固件 `GetSystemInfoJson()`。

最小响应：

```json
{
  "websocket": {
    "url": "wss://api.example.com/xiaozhi/v1/ws",
    "token": "device-session-token",
    "version": 1
  }
}
```

可选响应：

```json
{
  "server_time": {
    "timestamp": 1787890000000,
    "timezone_offset": 480
  },
  "firmware": {
    "version": "1.0.0",
    "url": "https://api.example.com/firmware/device.bin",
    "force": 0
  }
}
```

生产环境应让 OTA 接口根据 `Device-Id`、`Client-Id`、固件版本和设备型号生成或返回有效 Token。云厂商密钥不得下发给设备。

## 6. 音频编解码边界

统一运行时内部使用：

```text
PCM signed 16-bit little-endian
16000 Hz
单声道
```

设备上行：

```text
ESP32 Opus → 服务端 Opus 解码 → PCM → ASR
```

设备下行：

```text
TTS PCM → 服务端 Opus 编码 → ESP32 播放
```

建议建立独立的编解码组件：

```python
class AudioDecoder:
    async def decode(self, frame: bytes) -> list[bytes]: ...

class AudioEncoder:
    async def encode(self, pcm: bytes) -> list[bytes]: ...
```

首期实现：

```text
OpusDecoder
OpusEncoder
PcmPassthroughDecoder
PcmPassthroughEncoder
```

H5 当前 PCM 链路不得经过 ESP32 `Opus` 编解码器，避免改变 H5 的延迟和行为。

## 7. 多设备接入模型

设备协议网关通过 `DeviceProfile` 描述设备能力：

```python
DeviceProfile(
    device_type="esp32",
    protocol_version=1,
    input_codec="opus",
    output_codec="opus",
    sample_rate=16000,
    channels=1,
    frame_duration_ms=60,
    supports_mcp=True,
)
```

未来 T5 只增加设备适配器和 Profile，例如：

```python
DeviceProfile(
    device_type="t5",
    protocol_version=1,
    input_codec="pcm_s16le",
    output_codec="pcm_s16le",
    sample_rate=16000,
    channels=1,
    frame_duration_ms=20,
    supports_mcp=False,
)
```

统一运行时只接收以下内部事件：

```text
AudioInputFrame
UserSpeechStarted
UserSpeechStopped
UserAbort
TranscriptPartial
TranscriptFinal
AssistantTextDelta
AssistantAudioFrame
GenerationCancelled
SessionClosed
```

设备差异只能存在于：

```text
握手解析
输入音频解码
输出音频编码
控制消息映射
设备能力映射
```

## 8. 多端隔离

固定保留独立入口：

```text
/xiaozhi/ota/
/xiaozhi/v1/ws
/h5/ws
/realtime/webrtc
```

H5 继续使用当前：

```text
PCM 输入
PCM 输出
H5 消息格式
H5 VAD
H5 UI 状态
```

ESP32 使用：

```text
Opus 输入
Opus 输出
小智设备消息格式
ESP32 状态语义
```

两个端仅共享：

```text
统一会话运行时
ASR/LLM/TTS Provider
取消与打断机制
可观测性
```

不得通过修改当前 H5 `handler()` 来实现 ESP32 兼容。应新建独立的 `device_server.py` 或独立设备网关入口。

### 9.1 `xiaozhi-esp32-server`

优先复用其：


### 9.2 Pipecat

作为服务端实时全链路核心：

```text
音频输入

TTS 流式输出

```

当前项目已使用 `pipecat-ai==1.8.1`，后续应将 ESP32 和 H5 的公共流程接入统一运行时。

### 9.3 LiveKit Agents

复用其成熟的实时交互能力：

```text
轮次检测

```

当前项目的 `PreemptiveGenerationCoordinator` 应继续作为独立组件，不放入具体设备网关。

## 10. Provider 契约与一键切换

统一 ASR：

```python
class ASRProvider(Protocol):
    provider_id: str

    def recognize(
        self,
        audio: AsyncIterable[bytes],
        cancel_event: asyncio.Event,
    ) -> AsyncIterator[ASRPartial | ASRFinal]: ...
```

统一 LLM：

```python
class LLMProvider(Protocol):
    provider_id: str

    def stream(
        self,
        request: LLMRequest,
        cancel_event: asyncio.Event,
    ) -> AsyncIterator[LLMStreamEvent]: ...
```

统一 TTS：

```python
class TTSProvider(Protocol):
    provider_id: str

    def synthesize(
        self,
        text: str,
        cancel_event: asyncio.Event,
    ) -> AsyncIterator[TTSAudioChunk]: ...
```

首期 Provider：

```text
ASR：阿里云 DashScope Paraformer Realtime v2
LLM：阿里云通义千问 Qwen、DeepSeek、OpenAI 兼容接口、Dify Chatflow
TTS：火山引擎 BigTTS v3
```

配置示例：

```env
ASR_PROVIDER=dashscope
LLM_PROVIDER=qwen
TTS_PROVIDER=volcengine
```

切换 LLM：

```env
LLM_PROVIDER=deepseek
OPENAI_COMPATIBLE_BASE_URL=https://api.deepseek.com
OPENAI_COMPATIBLE_MODEL=deepseek-v4-flash
```

设备 WebSocket 地址和固件均不变化。

“任意云端 API”的边界是：实现统一 ASR、LLM 或 TTS Provider 契约的 API。未知厂商不能依靠网关猜测请求格式。

## 11. 会话、打断与错误处理

统一状态：

```text
READY → LISTENING → THINKING → SPEAKING → READY
```

打断流程：

```text
设备发送 abort
  ↓
取消当前 TTS
  ↓
清空未播放音频
  ↓
取消当前 LLM 生成
  ↓
保留已播放文本
  ↓
恢复 LISTENING
```

优先复用现有：

```text
CancellationScope
generation_id
PlaybackLedger
_ASRTurnTaskRegistry
PreemptiveGenerationCoordinator
```

统一错误码：

```text
AUTH_FAILED
UNSUPPORTED_AUDIO
ASR_FAILED
LLM_FAILED
TTS_FAILED
PROVIDER_NOT_CONFIGURED
SESSION_TIMEOUT
PROTOCOL_ERROR
```

TTS 失败时必须发送 `tts.stop` 或等价结束事件，避免固件永久停留在 Speaking 状态。

## 13. 实施阶段

### 第一阶段：ESP32 真实兼容闭环

实现：

```text
OTA 配置返回
WebSocket 握手
请求头认证
协议版本 1
裸 Opus 上行
裸 Opus 下行
listen start/stop
abort
stt
tts start/sentence_start/stop
llm emotion
error
```

验收：ESP32 只修改 `CONFIG_OTA_URL` 后，可以完成连接、识别、流式生成、流式合成和播放。

### 第二阶段：公共全链路运行时

将以下两条链路接入统一运行时：

```text
ESP32 WebSocket → 统一运行时
H5 WebSocket → 统一运行时
```

验收：H5 原有 PCM 消息和交互不变，ESP32 使用 Opus 消息，两者可同时连接且互不影响。

### 第三阶段：多设备适配器

增加：

```text
DeviceAdapterRegistry
DeviceProfile
AudioCodecRegistry
MessageCodecRegistry
```

验收：模拟 T5 设备只增加适配器，不修改核心会话流程。

### 第四阶段：多端实时能力

使用 Pipecat 和 LiveKit Agents 增加 WebRTC/移动端适配器，不改变 ESP32 WebSocket 协议。
