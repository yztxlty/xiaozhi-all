# 幽光旧系统语音链路审计

> 状态：基线生效
> 版本：v0.1
> 更新日期：2026-08-28
> 审计对象：本地 `gaowei/chat` 源码快照

## 结论

旧系统本质是“录音转文字、文本消息、完整音频文件播放”的消息式语音聊天，不是持续双向传输、可实时打断的语音会话。新项目只复用业务语义和已有角色资产，不复用该语音主链路。

## 当前链路

### 微信小程序

`WechatSI 整段录音识别 → 最终文本 → 普通 JSON 消息 → Dify/Coze 完整回复 → 火山 TTS 完整 MP3 → TOS URL → 客户端播放`

### 移动端应用

`整段录音文件 → /voiceConvertText → 文本消息`。审计时该接口仅返回固定测试文本，腾讯 ASR 类存在但没有业务调用方。

### 硬件聊天模块

接口接收已经识别好的文本，按标点触发语音合成并以 Base64 JSON 下发音频片段；它没有上行音频、语音识别、VAD、打断确认和播放进度闭环。

## 语音识别、大语言模型和语音合成现状

| 环节 | 实现 | 结论 |
| --- | --- | --- |
| 语音识别 | 微信 WechatSI、未接入的腾讯录音识别、移动端 测试桩 | 平台割裂，非统一流式语音识别 |
| 大语言模型 | Dify、Coze | 上游可流式，但主聊天等待完整回复后才发给客户端 |
| 语音合成 | 火山为主，残留腾讯实现 | 主链路生成完整 MP3、解析时长、上传对象存储 |
| 传输 | JSON WebSocket | 没有标准二进制音频帧、背压和代次控制 |

## 关键问题

1. 延迟按语音识别、大语言模型、语音合成、上传、下载串行累加。
2. 没有 `turn_id`、`generation_id`、取消树和播放确认，无法可靠打断。
3. 44.1kHz PCM、8kHz语音识别、16/24kHz语音合成并存，格式和重采样策略不统一。
4. Provider 分支散布在业务代码，模型切换只是向 Dify 传递 `model_id`。
5. Coze 同步事件迭代可能阻塞异步服务；语音合成分块缺少背压和顺序确认。
6. 音频通过 Base64 JSON 下发，增加体积和解析开销。
7.语音合成WebSocket 存在关闭 TLS 证书校验的实现，不能进入新项目。
8. 缺少语音识别partial、大语言模型首字延迟、语音合成首包、首音和打断延迟的生效指标。
9. 缺少完整语音链路、弱网、打断和长稳自动化测试。

## 审计证据索引

- `chat-web/src/components/message/voice-mp.vue`：WechatSI 整句识别。
- `chat-web/src/components/audio/index.vue`：完整录音文件上传。
- `chat-web/src/components/message/input-send-bar.vue`：识别文本按普通消息发送。
- `chat-ai/controller/system.py`：`voiceConvertText` 测试桩。
- `chat-ai/common/ws_protocol.py`：JSON 文本事件协议。
- `chat-ai/controller/ws_chat.py`：完整 LLM 回复后生成音频文件；另有文本入口的 hardware_chat。
- `chat-ai/common/chat_message.py`：完整 MP3、时长解析与 TOS 上传。
- `chat-ai/third/dify.py`、`chat-ai/third/coze_agent.py`：LLM 流式事件最终聚合。
- `chat-ai/third/volcengine/ttsWebSocket.py`：TTS 分块和 TLS 配置。

审计文档不保存任何旧系统密钥、令牌、证书或真实用户数据。
